Policy configuration · prototype

Policy is recorded as data, in either app

Two no-code front ends over one policy record. The form is replaceable UI; the record, its structure and its versions are what the decision and reasoning engines read. Switch platform to see the same record written from either. Turn on field bindings to see the record path behind every control — rank objectives, edit a rule, move a weight, accept a recommendation and recalibrate.

One write path, two front ends

Both apps write through their own platform layer, then converge on the same data-layer contract. Nothing in the policy store knows or cares which app produced the change — only that it arrives keyed, versioned and attributed.

Resolution order

Weights are not stored per persona. One company baseline is derived from the ranked objectives, scope overrides sit on top within a bound, and the engine resolves the effective value at read time. This is the table the data team has to be able to produce for any traveller, in one hop, at booking speed.

Read-time resolution
1 · BaselineDerived from objective rank. Rank sets objective weight (95 / 80 / 78 / 70); each objective distributes to its strands by a fixed factor. 2 · Scope overrideStored only where it differs. Absent means inherit — no row is written for an unchanged strand. 3 · BoundOverride clamped to ±20 of baseline. A value outside the bound is rejected at write, not silently corrected. 4 · TravellerNot modelled here. When added it follows the same rule and the same bound, one level down. ResultNine effective values, with the level each came from, returned as one object to the reasoning engine.
Why it matters for the store

Storing resolved values per persona would mean rewriting every persona whenever an objective moves rank. Storing the deltas means one write, and the fan-out happens at read.

The cost is that resolution has to be fast and identical everywhere it is computed — so it belongs in the data layer as a view or function, not repeated in each app and each engine.

Version lifecycle and gates

A policy version is immutable once published. Everything before publish is a draft that can be edited freely; the gates decide when it stops being a draft. Move the stages in the app to see the current position.

What changes at each transition
DraftEditable by the AM. Nothing is exposed to the engines. AI extractions land here as unaccepted suggestions. CI reviewRecord frozen for structure, open for correction. CI resolves every extraction and every validation error. Client sign-offRead-only. A signed diff against the previous published version is generated and stored with the record. PublishedVersion becomes immutable, gets an effective-from timestamp, and a publish event goes on the bus. The prior version stays queryable for rollback and for re-running a past booking decision.
Immutability and replay

Every booking decision stores the policy version it was evaluated against. That is what makes a decision auditable a year later, and it only works if published versions are never edited in place.

Corrections after publish are a new version, not an update — which is why the draft path has to be cheap enough that nobody is tempted to shortcut it.

What each engine reads

The same record serves two different consumers with different tolerances. The decision engine needs certainty and speed; the reasoning engine needs the ranked intent. Splitting them is why policy is captured as four distinct shapes rather than as prose.

Decision engine — fixed and flex

Deterministic. Evaluates hard constraints as filters and flex rules as conditional passes with a captured reason. No ranking, no judgement, no model call.

  • Reads fixed[] as predicates that remove options
  • Reads flex[] with parameters as conditional passes plus a reason requirement
  • Reads capture[] to know what must be collected before a request is valid
  • Must resolve in milliseconds and be explainable as a rule reference, not a score
Reasoning engine — objectives and weights

Ranks what survives the decision engine. Reads intent in the client's own words alongside the numbers, which is why the objective text is stored, not just its strand mapping.

  • Reads objectives[] in rank order, with the client's phrasing
  • Reads resolved weights{} for the traveller's scope
  • Reads provenance so it can cite the clause behind a recommendation
  • Tolerates latency and returns a ranked set with reasons, never a hard block
The boundary the data team is being asked to hold

A rule that can be evaluated deterministically must never end up as a weight, and an intent that cannot be evaluated deterministically must never end up as a fixed rule. The app enforces this at capture — four tabs, four shapes — because once it is wrong in the record, both engines behave wrongly and neither can tell you why.
